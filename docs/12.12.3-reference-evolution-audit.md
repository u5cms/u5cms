<a id="zwei-bestätigte-kollateralschäden"></a>
## Two confirmed regressions

**1. Custom applications were still restricted by globally reserved request fields.** A direct PHP application using `connect.inc.php` handles `c[]`, `n[]`, `p[]`, `u5prvldd[]` and cookie collections `u[]`, `p[]`, `hp[]` unchanged in the original. The global PHP compatibility check returned HTTP 400 even though that application invoked no CMS route or login consumer. The first review had still drawn the global boundary too broadly.

`request.inc.php` now only defines type validation. Actual CMS consumers validate their routing, preview, language, form targets and authentication cookies in the relevant context. Form targets are rejected before the first HTML output. Custom bootstrap applications retain their collections; inappropriate collections at actual text/login boundaries still return HTTP 400. An unused session cookie does not affect Basic authentication. [First actual original/target observations](../tests/reference-first-observations.json).

**2. The real CSV import silently changed older input.** A tabular import containing a backslash before quotation marks succeeded in the original but was stored differently under the new escape default, although the import reported success. The direct reader-class test alone had not verified this interface path. [Reproduction before correction](../tests/reference-csv-before-fix.json).

Unmarked import requests and the interface default again use the original backslash format. Standard CSV with doubled quotation marks and literal backslashes remains explicitly selectable. The reader and internal intermediate output use the same selected escape mode. Unknown or collection-valued format selections are rejected before HTML output or file writes. The actual import path checks both formats, including a trailing backslash; existing direct CSV reader tests are retained. Existing data and the historical internal semicolon substitute `,.` are not reinterpreted.

The other 14 branches do not contain the two causing PHP compatibility changes. Their historical import/bootstrap contracts pass the direct reference suite; they need no corresponding application correction.

## Correctly interpreting absent native mbstring

The initially intended complete original comparison without native mbstring already fails at the original Basic login. A separate probe demonstrates incorrect UTF-32 byte order/numeric entities in the old polyfill; the current polyfill returns correct values. This combination, which already failed on the original, was neither declared a successful baseline nor presented as new collateral damage.

12.12.3 and 12.12.4 pass the same flows without native mbstring: once with intl, once without intl/GD. These additional two series explicitly compare against the **previously saved successful** original reference with native mbstring. Each passes 106 target assertions without differences. The evidence records zero new original assertions for these runs; they demonstrate preserved functionality in an additional runtime profile, rather than a successful original run in that profile. GD-free comparison profiles test pages/forms/CSV, not image processing without GD.
