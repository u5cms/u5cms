## Summary

The handbook's examples were exercised independently against the actual u5CMS source. This page explains how to repeat the exercises and what their observations establish.

**Audience:** maintainers and documentation authors. **Version:** 12.10.0 baseline with the stated header correction. **Scope:** disposable local exercises.

## Repeat the independent exercises

Use an isolated local database server and a disposable test database. The walkthrough needs permission to create and drop its randomly named fixture database. The ownership exercise uses temporary tables in the configured test database. Do not point these commands at production.

Prerequisites are the branch's supported PHP with its required extensions, MariaDB, Python 3, the `openssl` command, Node.js, Playwright and a compatible Chromium installation. Use the existing repository dependencies; a full CMS login credential is generated by the fixture rather than supplied in these commands.

```sh
export U5CMS_TEST_PORT=3307
export U5CMS_TEST_DB=test
export U5CMS_TEST_USER=root
export U5CMS_TEST_PASSWORD='YOUR_LOCAL_TEST_DATABASE_PASSWORD'
export U5_TEST_PHP=php
export U5_TEST_PLAYWRIGHT=/absolute/path/to/playwright
export U5_TEST_BROWSER=/absolute/path/to/chromium
export U5_DOCUMENTATION_OUTPUT=/tmp/u5cms-documentation-output

"$U5_TEST_PHP" tests/documentation-ownership.php
python3 tests/documentation-walkthrough.py
```

`U5_TEST_BROWSER` can be omitted when Playwright's default installed Chromium is suitable. `U5_DOCUMENTATION_OUTPUT` is optional; without it, output stays within the walkthrough's temporary directory. With it, the walkthrough retains its observations, management-page screenshot and local PHP server log for inspection. Treat fixture logs as local diagnostics and review them before sharing.

The scripts are [`documentation-ownership.php`](../../tests/documentation-ownership.php), [`documentation-walkthrough.py`](../../tests/documentation-walkthrough.py), [`documentation-trusted-browser.cjs`](../../tests/documentation-trusted-browser.cjs) and [`documentation-content.cjs`](../../tests/documentation-content.cjs). The stable acceptance workflow runs the ownership exercise and the browser walkthrough.

## Findings that shaped the teaching

**Trust is not the ordinary session.** Removing the ordinary session cookies allowed trusted resumption. CMS logout instead revoked the current registration. Clearing every cookie lost the local credential while leaving a server place occupied. Those observations explain the replacement procedure in the guide.

**Access policy is not stored ownership.** Domain scope changed the selected rows. Returning to personal scope restored the original selection, and the stored owners remained byte-for-byte unchanged.

**Rendered content is not proof of a populated translation.** An empty English field displayed first-language fallback content. The editing guide therefore asks the editor to inspect the intended source field.

**HTML boundaries are not a universal escape.** A raw closing CMS marker was consumed in an initial literal-text example. Encoding the brackets produced the exact intended text. The guide teaches that tested representation rather than assuming HTML makes every CMS marker inert.

**Storage is not the final export.** A raw `datacsv` value includes internal escaping. The actual backend table and CSV endpoint returned the original accented, CJK and supplementary Unicode text. The final test checks those user-facing paths.

**A named update is not a full rebuild.** The unique exercise text became a real search result after a named update; the full-rebuild watermark stayed unchanged.

## A failure found through the browser

The initial trusted-page run failed on the page's own registration form. With `Referrer-Policy: no-referrer`, Chromium sent `Origin: null`; the unchanged origin guard rejected the POST with HTTP 403. The page now uses `same-origin`, retaining a valid origin for its own submission and withholding referrers from other origins.

The complete repeated walkthrough passed after that one-header correction. It still rejects an incorrect CSRF token and a cross-origin registration request. The exercise therefore verifies the successful operation and the relevant denials together.
