# u5CMS 12.11.2: review against main and restore regression

This release follows `12.11.1` (`16377863d62f0b9a53235fbfabf236d1b18a425c`).
It retains the backend and image-format work inherited through
`12.10.1-Support-More-Image-Formats`; it does not start a new line from main.
The comparison baseline is main at
`9d366253417822c279692767b89dcf1ff0388c5c` (12.9.5). Before this follow-up,
that comparison covered 171 files, including bundled image decoders, both SQL
seeds, backend changes and the 12.11 migration.

All eight remote branches were checked. The functional changes of
`12.9.6-Misc-Backend-Optimizations` are already in this ancestry (its remaining
difference from the corresponding ancestor is the displayed version).
`php9_compat` is a separate, extensive refactoring; it has not been merged into
this maintenance release. Main and the earlier release branches are unchanged.

## Reproduced defects corrected

| Area | Correction |
| --- | --- |
| Restore of renamed layouts | File backups include the layout-role map, migration checkpoints, guarded row journals and pending rename state, together with the existing files and reset templates. |
| SQL backup fidelity | `SHOW CREATE TABLE` preserves actual engines, charsets, collations, generated expressions, defaults, comments and index prefixes. Stored values use their own column encoding or binary representation. Generated columns are recomputed on import. |
| Numeric and old-schema data | Explicit AUTO_INCREMENT zero, zero dates, binary/bit values, decimal values and FLOAT precision survive a real import. |
| Backup failures and memory | Dumps and ZIPs are staged before publication; prior completed backups remain available. SQL generation writes hexadecimal values in chunks. Failure responses are prepared before HTML output so they return HTTP 500. Missing ZIP support leaves no temporary file. |
| Single-byte JSON | Valid Windows-1252 JSON is parsed without changing its original byte encoding. Literal selectors/bindings remain literal; actual embedded HTML and resource URLs migrate. Type guessing recognizes these JSON sources. |
| Repair after an earlier update | A separate 12.11.2 checkpoint handles completed installations. Earlier pending plans finish first. Guarded previous row backups can repair affected JSON only when the complete current row still equals the saved earlier result. Later edits take precedence. |
| Wrong save endpoint | The ordinary page endpoint rejects actual C and other non-P objects before writing. Its conditional update also requires the P type. |
| Dependency display | Localization, orphan scans and repository highlighting recognize typed flat exports, encoded names, escaped JSON paths, CSS imports and static module/function references. File boundaries prevent matching similarly named files or `.backup` suffixes. |
| Preview synchronization | Waits for the target document parser before replacing its body, avoiding intermittently broken search forms. A partially parsed real iframe reproduces the old behavior and verifies the correction. |
| Backend timer | The welcome timer tolerates replacement of the status document during a save. |

New dumps have unique timestamps and suffixes. Earlier requested dumps are
retained, including multiple backups made on the same day.

## Character encodings and migration boundaries

The supplied MariaDB schemas store text as `utf8` / `utf8mb3`. The legacy CMS
connection uses `SET NAMES latin1`, and ordinary HTML/forms use Windows-1252.
Those are separate layers: MariaDB converts between the connection encoding and
stored column encoding. The migration reads the actual column metadata and raw
stored bytes. Existing `utf8mb4` columns remain `utf8mb4`.

There is no blanket database conversion, entity decoding or conversion of
ordinary page content to a different encoding. Actual Latin1 columns are
additional compatibility fixtures, not the format proposed for normal installs.
The single-byte JSON conversion has an exact round-trip check for all 256 byte
values. If old row backups are missing or a row was subsequently edited, the
repair does not reconstruct unknown original text by guessing.

The last `!` still selects the extension. Reset baselines stay directly in `r/`
and preserve custom content and renamed roles. No `code-templates` directory or
MIME `.htaccess` override is introduced. Both SQL seeds already contain the typed
names and matching source references from 12.11.1; no seed change is needed for
these runtime corrections.

`runonce.php` is removed only after the 12.11.2 completion marker exists. A failed
or interrupted repair keeps its checkpoint and can resume on the next backend
visit. The existing 12.11.0/12.11.1 on-disk identifiers remain readable.

## Validation

The suite uses disposable databases and copied installations. It exercises both
SQL seeds, legacy and already-completed updates, interruptions, concurrent edits,
custom reset baselines, retained history, source files and actual browser forms.
The additional web suite is enabled with `U5CMS_MAIN_AUDIT=1`; use
`U5CMS_MAIN_AUDIT_ONLY=1` to run that suite alone.

The follow-up also covers:

- SQL and ZIP extraction/import into new locations/databases, including a renamed
  active layout and its custom reset baseline;
- compressed and plain dumps, preserved previous dumps, deliberate custom-view
  rejection, cyclic-directory failure and missing ZIP support;
- both editor panes, queued saves, edits during a request, stale versions,
  rejected requests, retries and several viewport sizes;
- normal metadata forms and album captions, including edits while saving;
- Basic and cookie-session authentication, expired editor logins/CSRF and
  application-level administrative permissions;
- protected file and thumbnail access before conditional caching, unchanged 304
  responses, changed-file 200 responses, path boundaries and thumbnail pixels;
- typed-code localization/orphan results and live repository filters;
- the inherited browser-side image conversion and multipart publication suite.

Validated with PHP 8.3.6, MariaDB 10.11.14, MySQL 8.0.46 and Chromium 156:

- 1,427 core/database/stress assertions;
- 51 frontend, 98 backend and 463 extended browser/restore checks per database engine;
- 94 image checks and 33 inspected published outputs;
- PHP syntax validation across the changed application files and test helpers.

The migration stress fixture contains about 40 MB of text across 2,500 rows,
5,000 history rows and a 4.2 MB BLOB. Its worker has a 64 MiB PHP limit. The
separate backup stress fixture exports one 24 MiB row under the same PHP limit;
it is removed before the ordinary workflow tests. Restore validation uses a
larger memory/packet budget to import and compare the actual SQL output.

## Scope of the backup checks

The built-in dump exports table schemas and data. Custom views produce an
explicit failure, preserving earlier dumps; stored routines, triggers and events
are outside this exporter. Full-server tools remain appropriate for such custom
database objects. SQL and ZIP backup jobs are separate requests; an actively
changing installation is not an atomic database-plus-files snapshot. The code
migration lock coordinates code exports, renames, resets and these backup jobs.

Tests establish behavior for the tested schemas, runtimes and failure cases.
They cannot certify every custom database, PHP memory limit or server setup.
The measured 64 MiB results are for the specified fixtures, with backup email
sending disabled; very large individual rows and email attachment assembly have
their own memory requirements. No production database was modified or deployed
as part of this audit.
