# u5CMS 12.12.1: rename and cumulative review against main

Date: 30 October 2026. Parent: OIDC branch `12.12.0-OIDC`, commit
`acdd8d6cf362c93803e94897336d347e26d1dba6`. Production main remains at
`9d366253417822c279692767b89dcf1ff0388c5c` (12.9.5).

This branch retains the cumulative 12.9.6, 12.10, image-format, MIME, 12.11,
search and OIDC work. It does not replace that development history with a fresh
copy of main. The separate historical `php9_compat` branch and parallel 12.9.6
head were inspected when selecting the cumulative base; they are not silently
merged into this release. The project-wide review requirement is recorded in
[AGENTS.md](../AGENTS.md).

## Corrections and preserved intent

* Ordinary renames now use one candidate scan per relevant table, one reference
  transformation per candidate and writes only for actual changes. Files use a
  single directory pass. Immutable guarded plans retain original row bytes,
  template before-images, policy and file operations for retry after interruption.
* Resource, history, login, template, form, free-image, relative-family,
  multi-language and album dependencies retain their configuration policies.
  Video poster resources/directories follow the video. Basic file access rules
  keep their membership hashes and move their absolute password-file path.
* Bracket protection uses no magic sentinel strings. Literal headings and the
  old sentinel text survive. The typed-code parser also stops rewriting resource
  names that are merely heading text. Real nested links still follow their target.
* JavaScript variables/arrays and CSS selectors remain literal during ordinary
  renames too. Actual query targets, explicit inclusions and media paths follow
  the object, including JSON-escaped paths. Replacements do not cascade when a
  new name contains an old alias.
* Intranet-to-intranet renames keep membership. Leaving the `!` namespace clears
  membership as intended; the old condition cleared it for practically every
  target. Name-family matching no longer interprets `_` as a SQL wildcard.
* Each changed current resource gets one revision marker and invalidates its
  search text. Heading-only matches leave revisions untouched. A parallel search
  index cache refresh does not masquerade as a conflicting source edit.
* Page, metadata, upload, album-sort and file-delete writers coordinate with the
  existing mutation lock. Different mutations cannot run through an unfinished
  ordinary rename. Recovery backups remain possible and include its checkpoints.
* The browser reports success only after files, references, histories and exports
  have finished. The former timer and name-disappearance shortcut are removed.
  The history-only GET endpoint is retired; all mutation uses the authenticated,
  CSRF-protected request. Retry preserves archive/code HIADRI even after source
  ownership has moved, including inherited code-rename checkpoints.
* The cumulative review found a conflict-poll issue: a newer deleted tombstone
  could cause an archived editor to report a false conflict. The poll now selects
  the current nondeleted resource. Collation-equivalent target tombstones are
  retained and safely reused using their original database name bytes.

See [rename.md](rename.md) for the complete policy table, operations, failure
handling and rollback. Ordinary resource target names remain routable through
u5CMS sanitization; reserved template system names and unsafe destinations are
rejected before changing source rows. Existing code-extension restrictions and
12.11 migration/checkpoint identities are retained.

## Measured rename performance

The benchmark executes the **actual committed legacy** `sere13`, `sere13b` and
`loginglobals` functions, not an estimated query model. It includes legacy
language/album file probing and compares that subtotal against the complete new
ordinary rename, including its guarded journals and publication. The old subtotal
omits other old steps, so the comparison does not inflate the new implementation
by timing a smaller new operation.

Results are in [the machine-readable benchmark](12.12.1-rename-benchmark.json).
Both fixtures contain 955 files. Their legacy directory loop makes 858,845
existence probes. The new path enumerates the directory once. The sparse fixture
contains 5,000 resources and 25,000 histories, with one dependency per 100 rows;
the dense fixture contains 2,000 resources and 5,000 histories, all with dependencies.

| Fixture | Legacy reference SQL + files | Complete new rename | Speedup | Changed rows | Peak PHP memory |
| --- | ---: | ---: | ---: | ---: | ---: |
| sparse | 29.359 s | 0.319 s | 92.04x | 300 | 6.0 MiB |
| dense | 7.730 s | 3.917 s | 1.97x | 7000 | 6.0 MiB |

Every run verifies all 20 text columns in resources/histories and every file
against the legacy result or original bytes. The final engine also handles
important corrections outside that conservation fixture, such as protected
headings, encoded paths, video posters, no cascading aliases and preserved
intranet membership. The sparse/dense speed difference is expected: safety
journaling and conditional writes scale with the number of rows actually changed.

Large media are moved without copying or reading their entire contents at
runtime. A separate 128 MiB video fixture is checked with a full SHA-256 before
and after the rename. Tests also retain destination directories/files and verify
language/album variants and internal symbolic links.

## Limits and operation

These results establish the checked behavior, not a guarantee about arbitrary
site-specific PHP, every browser/server or every production dataset. Native
Firefox/WebKit, Apache/IIS-specific configuration, live eIAM/AGOV onboarding and
real provider logout acceptance still require the deployment's normal acceptance
checks. The HTTPS fixture is a real local protocol/TLS test, not live-provider
certification. Legacy SAML compatibility includes its existing mock path, not an
external live SimpleSAML federation.

This branch adds no mandatory identity-binding schema or new ordinary-rename
schema migration. OIDC stays opt-in and the optional verified-email binding table
retains its documented setup. Keep a matching database/file backup before release.
Do not remove pending rename or 12.11 migration journals to bypass an error.
Recover by resolving the named conflict and resuming the same saved operation,
or restoring both halves of a pre-operation backup. Main is unchanged and this
work has not been deployed.
