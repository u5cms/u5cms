<a id="grenzen-und-betrieb"></a>
## Limits and operation

The new PHP compatibility line requires PHP >= 8.2. New database/browser runs in this task used PHP 8.3; PHP 8.5 was used for syntax, source inspection, core contracts, IDN, mail construction and dependency installation. This does not certify an actual PHP 9 runtime.

Mail checks confirm executed constructor contracts and transport selection, rather than external delivery. Without intl, the old Laminas version could already fail on ordinary addresses because IDNA constants were absent; the new libraries supply that API without automatically changing CMS usernames. An isolated constructor case with a raw non-ASCII local part is rejected on both old and new sources. Complete EAI/SMTP acceptance is not inferred from it.

Malformed UTF-8 byte sequences do not always produce the same replacement-character count as deprecated utf8_decode; the demonstrated equivalence applies to valid UTF-8 and the documented default replacement character. Unknown installation-owned PHP/vendor callers and a real external federation provider are outside the accessible distribution. Public CMS configuration and supplied extension paths were checked; no production installation was changed.

Corrections do not automatically change stored identity keys. A planned native IDN-profile change still needs its own inventory review, as in the original CMS. Already migrated installations should restore a matching file/database state when rolling back; these corrections do not replace a migration backup.

Executed checks and source comparison found no further confirmed regression within scope after the corrections. This is local verification evidence, rather than GitHub CI or a production rollout.
